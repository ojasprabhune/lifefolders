# lifefolders

Personal logging app: one text/voice input, LLM tool-calling parser, structured timeline organized by date and category. Tracks nutrition, people, music, workouts, places, trips, sleep, learning, and tasks.

For setup and deployment details, see the [README](./README.md).

## Data model

The `logs` table (`id uuid, created_at timestamptz, raw_input text, parsed_type text CHECK, data jsonb, deleted_at timestamptz`) is the primary workhorse, storing timestamped entries across eight lightweight domains (nutrition, person, album, song, place, trip, sleep, task). Each new `parsed_type` is added via a migration that widens the CHECK constraint.

Two domains break from this JSONB-in-logs pattern:

- **learning** (`backend/migrations/0004_add_batch2.sql`): has real relational tables (`fields`, `resources`, `topics`, `resource_files`) because it needs efficient querying by field/topic/resource relationship, not just "insert and list by created_at." A `logs` row is still written per action (create/update/progress) so timeline history is preserved.
- **tasks** (`backend/migrations/0005_add_tasks.sql`): similar pattern — a real `tasks` table (title, category, due_date, status, is_exam, effort_minutes) and a related `task_checkpoints` table (spaced-review reminders for exams) for efficient due-date and status queries, plus per-action timeline entries in `logs`.

The JSONB-first convention is: unless there's a concrete querying need beyond date/type filtering (like "all tasks due in the next 7 days" or "relationship between resource and topic"), keep it in `logs.data` and add relational tables only when justified.

## Backend module map

- **main.rs** — bootstrap, route registration, CORS config, shared bearer-token auth middleware.
- **models.rs** — all entity structs (`NutritionData`, `PersonData`, `TaskData`, etc.) and dispatch enums (`Action`, `Parsed`).
- **routes.rs** — generic CRUD endpoints for `logs` (`/api/logs`); special-case handlers for entities needing side effects (`upsert_workout`, `handle_sleep`, `append_itinerary`, `transcribe`).
- **groq.rs** — LLM client (Groq API, tool-calling dispatch, system prompt, context injection).
- **learning.rs** — learning-domain-specific routes and side-effect logic (field/resource/topic CRUD, PDF ingestion, plan generation).
- **tasks.rs** — task-domain-specific routes and side-effect logic (task/checkpoint CRUD, fuzzy-match resolution, spaced-review generation).
- **commands.rs** — apply logic for the command tool group: reschedule/clear-due-date/status/recategorize/delete a task, start a focus session, plan the day, delete the last entry. Returns a notice, never a `logs` row (the exception being the task-history rows `write_history` writes). `plan_today` is the one command that reaches outside the tasks domain: it now just calls `dayplan::regenerate`, the same path the panel's own button takes, and reports back in a notice. It used to prepend a paragraph to `daily_notes.today_text`, on top of whatever you had written there; the plan is structured rows in the sidequests panel instead. Two things about the brief `dayplan::build_brief` produces are load-bearing and were both learned by watching the model get them wrong. The brief carries **only work that is due** — due today, already late, or a spaced review that has come due. The backlog was once offered alongside it as a second labelled group, on the theory that the model would treat it as a reserve; it treated it as permission, and an evening with three hours of real work came back with the whole backlog stacked behind it, running past bedtime, whereupon the app's own overflow suggestion was to drop the work it had just invented. `build_brief` clears `later` whenever `now_due` or `reviews` has anything in it. The backlog is still the fallback when genuinely nothing is due, under its own heading — a day with no work at all should not produce an empty script — and that is the one case where the prompt lets the model leave things out. And every sidequest carries a length, taken from `effort_minutes` or, failing that, parsed out of its note by `tasks::effort_from_text` — people wrote estimates into notes before there was a field for them. Without a length the model gave everything a flat thirty minutes, which is how three hours of research got scheduled into half an hour.
- **wishlist.rs** — things wanted but not done yet (`wishlist_items` table). Manual only, never auto-populated. `try_resolve` runs after every insert in `create_log` and crosses an item off when a matching album/song/place/trip/learning entry is finally logged.
- **search.rs** — plain-text search across every log (`GET /api/search`), `ILIKE` over `raw_input` and `data::text`. Deliberately unindexed and LLM-free; correct at this scale.
- **undo.rs** — the single-slot cmd+Z buffer. One HTTP request is one undoable action, however many things it touched: the mutating handler calls `undo::begin` once and every helper below it only `undo::record`s an `Effect`, so a reschedule keeps both its task snapshot and the timeline row it wrote. Undo replays the effects in reverse. A helper that calls `begin` itself would discard whatever its caller already recorded.
- **cadences.rs** — recurring habits. `Schedule` (every N days, or every N weeks on chosen weekdays, counted from `anchor_date`) is the core: everything downstream works in *occurrences* rather than calendar days, so a day the cadence wasn't due can't read as a miss, and a completion clears the latest occurrence at or before it. Completions themselves stay JSONB-in-logs; only the definition is relational.
- **rank.rs** — shared pairwise-comparison ranking engine used by album/place/trip domains.
- **usda.rs** — USDA FoodData Central API client for nutrition grounding.
- **wger.rs** — wger.de gym API client for workout import.

## LLM wiring

A single dispatcher in `groq.rs` sends one flat tool list with `tool_choice: "required"` to one Groq model at a time. The list is two groups concatenated by `tools(command_only)`: `log_tools()` (records of something that happened — `log_nutrition`, `log_person`, `log_task`, `log_album`, `log_song`, `log_learning`, `log_workout`, `log_place`, `log_trip`, `log_sleep`, `add_wishlist_item`, etc.) and `command_tools()` (instructions about things already tracked — `reschedule_tasks`, `set_task_status`, `delete_task`, `recategorize_task`, `start_focus`, `delete_last_entry`). One call picks either kind. Models are tried sequentially (`openai/gpt-oss-120b` → `openai/gpt-oss-20b` → `llama-3.3-70b-versatile`), with fallback on network/API errors.

`MODELS` is a rate-limit budget as much as a fallback chain. The prompt is fixed overhead — ~7.8k characters of `SYSTEM_PROMPT` plus ~14k of tool definitions, so roughly 6k tokens go up for every entry however short it is — and Groq's free tier meters tokens per minute *per model*, at around 8k. Two or three entries typed in a row exhaust one model, which is why there is a third with its own bucket. A 429 also carries a `retry-after`, and burning it (the refused request costs no budget) is cheaper than failing: `chat` waits out anything under `MAX_RETRY_WAIT` twice per model rather than falling through, because the browser's own ladder (`RETRY_DELAYS_MS`, 2s/5s/10s/20s) turns a three-second wait into a much longer one and shows "retrying…" while it does. If entries ever need to be cheaper still, the tool descriptions are the place to cut — they are the larger half and much of their prose repeats `SYSTEM_PROMPT`.

The one `SYSTEM_PROMPT` in `groq.rs` contains all domain-specific disambiguation rules (portion-size heuristics, exam vs. project classification, sleep parsing, etc.) — this is where cross-cutting logic lives, not in code branches.

Live app state is injected into the prompt per-request via helper functions (`learning::context_block`, `tasks::context_block`) called in `routes::create_log`. This is how the model resolves free text like "finished the chem lab writeup" against an existing task without needing to know its UUID — the open tasks list is appended to the prompt, and the LLM can reference them by title. Reuse this pattern (`*_context_block`) for any future module that needs to reference live state.

Three deterministic prefixes bypass the model's tool judgment in `parse()`: `task:` forces `log_task` via `tool_choice`, `wish:` forces `add_wishlist_item` (and is the *only* way to reach it — `tools()` leaves that tool out of the list entirely otherwise, so classifying wants by tense can't put things on the list uninvited), and `/` forces a command by narrowing the offered tools to `command_tools()` alone — there's no `tool_choice` that means "any of this subset", so the log tools simply aren't sent.

Inside an entry, four markers are parsed in Rust rather than trusted to the model, all in `tasks.rs`: `#tag` (category), `@time` (due time), `note:` (everything after it becomes the note verbatim), and a bare duration — `1 hr`, `40min`, `2h30` — which becomes `effort_minutes`. `strip_markers` keeps all four out of the title as a backstop. The duration one is the only marker without a sigil, so it has to be conservative: a number counts only when a unit word follows it, glued or spaced, which is what keeps `read 30 pages`, `the 1968 paper`, `ps5` and `level 2 of the course` intact. It reads the head of the entry only — a duration after `note:` is time already spent, not an estimate.

Task notes have two write paths on purpose. A typed entry **appends** a line (`update_task`'s `note = CASE ... note || E'\n' || $6`), because repeated check-ins should build a history. Editing the field via `PATCH /api/tasks/:id` with `note` **replaces** it, applied after `update_task` rather than through it — a correction has to be able to shorten a note, not only grow it. Both the timeline row editor and the expanded sidequest card use the replace path and fire `life-log-created` so the other view catches up.

`groq.rs` also holds three single-purpose non-tool-calling model helpers, all the same shape — small model, `reasoning_effort: "low"` to dodge the hidden-reasoning budget trap, `None`/passthrough on any failure so a Groq hiccup never writes something broken: `polish()` (voice transcripts), `sleep_insight()` (the solace blurb), and `plan_today()` (the day plan). Anything the blurb asserts as a *relationship* — a streak, a run, "in a row" — must be computed in Rust and handed over in a facts block (`sleep::build_facts`); the model reliably invents these when left to derive them from raw rows. The facts block is split into RECENT, TONIGHT and BACKGROUND sections, and the prompt forbids making the message about a BACKGROUND figure — a flat list let the model open on whichever number was most dramatic (usually the longest night, often a week old) instead of on how the last few nights are going. TONIGHT carries the one thing the coach can actually ask for: the median wake time over the last week and the bedtime that reaches the goal from it.

Sameness is its own failure mode there. The input barely changes day to day, so the model settles into one sentence skeleton with new numbers in it — no amount of "vary yourself" in the prompt fixes that on its own. Two things do: `sleep_insight_cache.recent_blurbs` keeps the last five messages and shows them back to the model as what not to repeat, and `sleep::angle_for` rotates the *shape* of the message through a seven-day list (open with the ask / one flat sentence / no reassurance / …) so the variation is decided in Rust rather than hoped for. This one uses `openai/gpt-oss-120b` rather than the 20b the other two helpers use, and a warm temperature — at 0.4 on 20b every day read identically.

Commands mutate existing state and return a `notice` (plus an optional `focus_session` for `start_focus`), never a `logs` row — `create_log` can legitimately come back with an empty `logs` array.

Entities that need side effects beyond "insert into `logs`" (workout session tracking, itinerary appends, learning resource ingestion, task create-or-update) go through special `Action` variants (`Workout`, `ItineraryItem`, `Learning`, `Task`) that get dispatched in `routes::create_log`; everything else becomes `Action::Entry(Parsed::...)` and goes straight into the `logs` table.

## Recipe: adding a new tracked entity end-to-end

1. **models.rs**: Define a `NewThingData` struct (the snapshot shape that goes into `logs.data` JSONB). If it requires live state or multiple SQL mutations, also define a corresponding `NewThingRequest` struct and add a `NewThing(NewThingRequest)` arm to the `Action` enum.

2. **groq.rs**: Add a `log_new_thing` function def to the tool list in `tools()`. Add a paragraph to `SYSTEM_PROMPT` explaining the domain's classification rules and expected phrasing. In the `parse()` function, add a match arm for `"log_new_thing"` that constructs either an `Action::NewThing(NewThingRequest{...})` (if it has side effects) or pushes an `Action::Entry(Parsed::NewThing(...))` (if it's plain JSONB).

3. **routes.rs** (if it needs side effects): Add a handler function (or inline code in the action-dispatch match) to call `NewThingRequest` side-effect logic, write a `logs` row via `sqlx::query("INSERT INTO logs ...")`, and return the result. Optionally, inject live state into the prompt via `NewThingRequest` → a `new_thing::context_block(&state)` function called in `create_log`.

4. **migrations** (if it needs relational structure): Create a new `00XX_add_new_thing.sql` migration. If it's simple JSONB in `logs`, just widen the `logs_parsed_type_check` constraint. If it needs real tables (like learning/tasks), define those.

5. **main.rs**: If you added new HTTP routes (e.g. `GET /api/new-things`), register them on the `api` router, protected by `require_auth`. Otherwise, the generic `/api/logs` endpoint covers CRUD.

6. **Frontend types.ts**: Add `NewThingData` (mirror of the Rust struct, matching JSONB keys). Add `'new_thing'` to the `ParsedType` union and the `Log['data']` union (and `Category` union if it's a filterable domain). If it needs a specialized row renderer, add a TypeScript type for it too (see `Task`, `Learning`, etc.).

7. **Frontend Row.tsx**: Add a case to the `summary()` function (one-line description of what happened), `badge()` (category/label pill), `rightSide()` (optional right-side metadata), and `Editor()` dispatch (inline edit form for the log snapshot). Reuse the `useEditor` hook and `EditorFooter` component as-is; they handle save/delete mutations.

8. **Frontend App.tsx**: Add `{value: 'new_thing', label: 'New Things'}` to the `FILTERS` array so it appears as a timeline filter. If you want a dedicated dashboard page (like `Learning.tsx`, `Sleep.tsx`), add a new hash route and a nav link.

9. **Frontend optional**: Add a page like `Learning.tsx` or `Tasks.tsx` if a summary/dashboard view makes sense. Add a paragraph to `Guide.tsx` documenting example phrasing.

## Second pattern: direct-UI entities (not LLM-parsed)

Most domains are entered through the one text/voice input and the `groq.rs` parse loop (the recipe above). A few are **entered through dedicated UI instead** — the LLM is not involved — but they still write a `logs` row so they show up in the daily timeline like everything else. This is the pattern for anything with a live/structured interaction that doesn't fit "type a sentence": `daily_notes` (autosaving Today/Tomorrow scratchpad, `daily.rs` + `DailyPlan.tsx`) and `focus_sessions` (live countdown timer, `focus.rs` + `FocusTimer.tsx`).

How it differs from the recipe:

- **No tool def, no `SYSTEM_PROMPT` paragraph, no `parse()` arm, no `Action`/`Parsed` variant.** The frontend calls a purpose-built endpoint directly (`POST /api/focus-sessions`, `PATCH /api/daily-notes/:date`), not `POST /api/logs`.
- **Relational table + its own module** (`daily.rs`, `focus.rs`) registered in `main.rs`, same as `tasks.rs`/`learning.rs`.
- **A `logs` row is still written** at the meaningful moment (a focus session *ending* writes `parsed_type: 'focus_session'`; the migration still widens `logs_parsed_type_check`). Timeline rendering in `Row.tsx` (`summary`/`badge`/`rightSide`/`Editor`) is added exactly as in the recipe — the timeline doesn't care how the row got there.
- **Filtering** can piggyback on an existing chip instead of adding one: `matches()` in `App.tsx` groups `weight` under the `workout`/soma chip and `focus_session` under the `task` chip, rather than giving every sub-type its own filter.
- **A live session is server state, not tab state.** `focus_sessions` used to be ended from a `beforeunload`/`pagehide` handler, on the theory that the tab was closing — but those fire identically for a reload, so refreshing the page killed the timer. Nothing is ended on unload now. The row simply stays open, and `focusEngine.restoreFocusSession()` asks `GET /api/focus-sessions/active` on load and adopts it, pause state included; a session whose planned time ran out while nothing was watching is closed there instead, capped at `planned_minutes` (the same cap, for the same reason, as the open-session check in `commands::StartFocus`). localStorage is only a first-frame cache — the server wins.
- **Auth edge case**: `beginFocusSession` must not **await** `audio.resume()`. A suspended AudioContext only resumes inside a user gesture, and the day plan's play button starts a session from an effect after navigating — the click is over by then, so awaiting it hangs forever and no session is ever created, silently. The chime is worth less than the timer.

`focus::end_session` still lives *outside* the `require_auth` layer and checks the token itself (header or body), left over from the beacon that needed a header-less request. Nothing sends the body form any more; keep the pattern in mind if a `logs`-writing action ever again has to fire from somewhere a bearer header can't reach.

The planner's header is rendered before its plan has loaded, and the body's height animation runs on the plan *arriving* as well as on the section being toggled (`arrived` in its dep list — on mount there is no body to animate yet, and by the time there is, neither of the other deps has changed). Waiting for the fetch and mounting the whole thing at once let the day's sections settle where the script was about to be and then shoved them half a screen down. The selected day itself is remembered in `lastPanel.ts` alongside the panel route — today is stored as the word rather than the date, so a tab left open across midnight comes back to the new today.

The third of these is **dayplan.rs + DayPlanner.tsx**, "the script" — the day laid out as blocks, above the sections in the sidequests panel, and only when *today* is the selected day (`selected === todayStr`): the panel's default view isn't a day at all, it's the whole backlog, and a plan with a "now" in it has no business there. It is worth understanding one decision: **a block stores a length and an order, never a clock time.** The times are derived by walking the list from `starts_at`, so inserting a break in the middle re-times everything below it without rewriting a single row, and there is no state that can be internally inconsistent. `pinned_start` is the escape hatch for something at a fixed hour; a pin already in the past is ignored, because a plan that runs backwards is worse than one that runs late.

The section's open and close are three things moving together and all three have to agree or it reads as broken: the per-block cascade (staggered off `--i`, and off `--r` on the way out so the last line leaves first), the spine's `clip-path` draw (its duration computed from `--n` so it finishes *with* the last block rather than well before it), and the body's own height, animated in JS because `auto` isn't animatable and whatever sits below has to slide rather than jump. A drag is the same split: the pointer offset is written straight to the held row's style every frame, while the index it would land on is state, because that one re-lays-out its neighbours. Pointer capture is taken at the 4px threshold, not on pointerdown — capturing on press retargets every later mouse event to the `<li>`, so the `dblclick` that opens a block's label editor was delivered against the row rather than the label inside it and never reached its handler. That editor writes `plan_blocks.label` only: a line of the script can say "chem lab — just the writeup" for one day without renaming the sidequest. Target is measured against the rows' *original* rects, captured at pointerdown — against the live ones the answer oscillates as they slide out of the way. Three traps in there: the close needs its own keyframes rather than the opening ones with `animation-direction: reverse`, because a finished animation only re-runs when its *name* changes; the height keyframes must carry `margin-top` too, or the body's 10px margin stands at zero height until unmount and snaps; the entrance animation has to be **taken off the rows once it has run** (`.plan-settled`), because reordering a keyed list moves the node with `insertBefore` — which takes it out of the tree and puts it back, and that restarts any CSS animation still attached to it, so a drop replayed the dragged row's own arrival. Freezing `animation-delay` is not enough (though it is separately necessary reasoning: *raising* a finished animation's delay shifts its active window back over the current time and re-runs it, which is why toggling `animation: none` on and off during a drag replayed every row). The `.plan-settled` rule must stay above the `.closing` rules, which set their own animation at equal specificity and win on source order; and `.planner-body` needs `margin-left: -22px; padding-left: 22px` so the `overflow: hidden` the height animation requires doesn't clip the dots sitting outside the content box.

`build_brief` hands each group to the model **longest first** (`estimate_of`), and the prompt tells it to keep that order: left alone it worked down the list it was given, so a half-hour errand opened the day and the ninety-minute piece of real work landed in the evening. Saying "keep the order" also, immediately, made it start echoing the brief's whole line — `lit paragraph [homework] due today, not_started, 90 minutes` — back as a block label, which is why `clean_label` now cuts at the *first* ` [` rather than only a trailing one. What keeps that safe is testing the tail: it only cuts when the bracket is followed by nothing or by the deadline the brief prints next, so a title that merely contains a bracket survives.

The LLM writes only the first draft, and only the work blocks. **Meals are placed in Rust** (`insert_meals`), because asking the model to position them by arithmetic drifted — dinner landed at 10:53pm in one run — and there is nothing to reason about: a meal happens at its hour, give or take. A block that would run into one is left whole and the meal slides after it, up to `MEAL_SHIFT_MAX` (45 min) — cutting a task in half to eat on the dot is worse than eating a quarter of an hour later. Only a block that would hold the meal up longer than that is split, and then the halves sum to the original length so an estimate is never quietly shortened. A meal keeps its full length wherever it lands. A meal only belongs to the day at all if its hour falls inside `[starts_at, ends_at]` (`meals_in_window`), and the same rule is applied again in `patch` when you move the bounds afterwards — planning at lunchtime and then pushing the start to quarter to four used to leave lunch sitting at the top, re-timed to quarter to four, because the block was already in the list and the times are derived. Relatedly, `regenerate` only resets `starts_at` to now when the stored start has **already gone by**; a start time in the future was typed on purpose. A **spaced-review reminder that has come due is real work for today** and goes into the brief's due-today group, at the top of it — `due_reviews` collapses the pending checkpoints down to one session per exam (an overdue 3d and today's 1d are the same revision) and the label carries a `study for ` prefix that `generate` strips before matching, so the block still links back to the exam. Being *last* in that group is what got them dropped whenever the day overflowed, which is also why the prompt now says every due-today entry must appear even if the day runs long: the app computes the overflow and asks, so omitting work is not the model's call to make.

`ends_at` defaults to `sleep::bedtime_target`, the same figure the sleep coach's TONIGHT block asks for, so the two cannot disagree — and that figure goes through `sleep::sensible_bedtime`, which floors anything outside 11pm–6am at 11pm. Median wake minus the goal is arithmetic, and a week of early mornings had it asking to be asleep by 8pm, which nobody does and which made an ordinary evening read as three hours of overflow. `sleepStats.bedtimeTarget` mirrors the floor for the same reason the rest of it is mirrored. Overflow past it surfaces a suggestion of what to drop, chosen by `choose_push`. The order of its two filters matters and is tested: **exam work is excluded first**, before the deadline test, because a study block for tomorrow's quiz is not a spare hour just because the quiz isn't today. Then work not due today (that is what "push it to tomorrow" means), and within whatever group survives, the *smallest* block that still clears the overflow — dropping three hours to save forty minutes is not a trade. Each filter is guarded so it can never empty the list.

When adding a new domain, pick this pattern over the recipe only when the interaction is genuinely structured/live (a timer, an autosaving field, a stepper) rather than a phrase the LLM could parse.

## Reading an entry before the server does

Typing a sidequest used to cost a Groq round trip - a second or more - before
anything but a grey placeholder appeared, which is the wrong shape for the way
the app is actually used: a burst of entries at the start of a day. Three
modules make that instant, and the split between them is the whole design.

`localParse.ts` reads a task out of a typed entry without the model. Four of
the fields are already deterministic in Rust rather than LLM-decided (`#tag`,
`@time`, `note:`, and a bare duration - see `tasks.rs`), so those are a
straight port and cannot drift; `effortFromText` and `bestMatch` are ports of
their Rust namesakes line for line. What is left is the title, a due-date
grammar, and the exam flag. **`parseTaskEntry` returns null unless it is
certain**, and certainty is deliberately narrow: a `task:` prefix, or a `#tag`,
or a date phrase *together with* a schoolwork/deadline word from a closed list.
A date phrase alone is not enough - "dinner with sarah friday" has to fall
through to the model - and the list is an allow-list rather than a deny-list
because no deny-list ever finishes. It also returns null when `bestMatch` finds
an open sidequest by that name: that entry is an update, and which fields an
update touches (and whether a note appends or replaces) is the server's call.
Everything that returns null keeps the plain pending row it always had. A row
of the wrong shape corrected a second later is worse than a second of nothing,
which is the trade the whole file exists to avoid.

`optimistic.ts` holds the rows that have been drawn but not confirmed. Home
creates them and the sidequests panel renders them and the two are not in the
same tree, so it is a module-level store with a subscription. The handover is
gapless on purpose: when the write lands the entry is **not dropped**, it is
given the id the server assigned, and the panel discards it only once its own
next fetch actually contains that id. Dropping it on the response leaves the
row missing for the length of the refetch, which is a hole opening mid-list.
Two consequences carry: `Log.localId` exists so the timeline can key the row
off it and the swap to the server's copy costs no remount and no replayed
arrival (verified - the DOM node survives, and its reveal keeps running over
the top of it); and `justParsed` is looked up by the same key, or the reveal
loses its markup the moment the response lands. An unconfirmed panel row wears
`.unsent`, which is only `pointer-events: none` - it looks finished, because
that is the point, but there is no id to act against yet. It also opens itself
with `unfold` rather than shoving its neighbours down in one frame, since it
arrives from the parse rather than through the panel's diff.

`cache.ts` is a first-frame copy of the day's timeline and the open sidequests,
and nothing in it is trusted longer than one fetch - the real request always
follows and replaces it. It exists because the backend sleeps after fifteen
idle minutes, so opening the app is regularly half a minute of empty panel. Two
things about it are load-bearing. The timeline is cached from **what is on
screen**, not from the last fetch: almost everything that lands in a day is
applied locally and never refetched, so caching inside `refresh` kept handing
back the day as it looked when you opened it. And `Tasks` seeds `tasks` from
the cache while deliberately leaving `previous.current` empty - the diff only
marks ids it has seen before, so the real list arriving cannot animate a
done-sweep or a reschedule against a cache that may be a day stale. Home warms
the task cache itself on a first-ever visit, because the local parse needs the
open sidequests to tell a new one from an entry about something tracked; on
every later visit the panel has already written it.

`outbox.ts` keeps unconfirmed entries on disk so closing the tab mid-request
doesn't take the sentence with it. **Nothing is ever replayed automatically**:
the backend has no idempotency key, so a request that succeeded and only lost
its reply would come back as a duplicate. Leftovers are handed back as the same
failed row a dead network produces, and retrying is a tap.

## Frontend architecture

Hash-based router (no library): `#/` = home (daily timeline), `#/music` / `#/sleep` / `#/tasks` / etc. = dedicated dashboard pages for complex domains.

`#/cadences/all` is the one route that breaks the panel/page split from both sides: it's a domain page, but rendered full-width like `guide` and `focus` because it exists to show every cadence's heatmap at once, which a half-width panel can't. It reuses the panel's `Heatmap` component verbatim and gets its data from `GET /api/cadence-completions`, a bulk endpoint that stays two queries however many cadences there are — the per-cadence route would have been one round trip each against a backend that sleeps between visits.

`#/sleep/all` is the second wall, same shape as the cadence one and reusing the same `.app.wall` container. Its entrance is **pure CSS** — every element sets an `--i` index inline and the keyframes in `styles.css` derive `animation-delay` from it. This started out on anime.js and was moved off it, for a reason worth keeping: a JS timeline re-runs whenever its effect re-runs, so the page replayed itself the moment the (slower) insight fetch resolved. The same bug bit `CountUp`, whose `format` prop was a fresh closure in its dep array — it now keys on the value alone with the formatter in a ref. CSS animations run on mount and are immune to both.

Two further rules that page keeps: SVG line-drawing uses `pathLength` (1 on the drift paths, 100 on the ring) so a dash animation needs no JS measurement of path length; and nothing animated may also carry meaning in the same property — the calendar's four shading levels live in `color-mix` backgrounds rather than `opacity` because an opacity animation was overwriting them. `prefers-reduced-motion` is one `animation: none` block; every animated property's base value is already its finished value, so nothing else is needed.

Sleep math shared between the panel and the wall lives in `frontend/src/sleepStats.ts`. Clock times there are measured from **6pm**, not midnight, so a 12:30am bedtime sorts next to an 11:30pm one; `NIGHT_ORIGIN_MIN`/`nightMinute` are that frame, and `sleep.rs::build_facts` does the same thing server-side. `bedtimeTarget` must keep agreeing with the coach's TONIGHT block — the ring and the blurb sit inches apart on that page.

`#/search` is a panel like those but is not a domain — it stays out of `DOMAINS` for the same reason `guide` does. It renders results with the shared `Row` component, holding them in local state so an edit made from search saves in place.

The `Home` page renders a daily timeline filtered by date and category. Category filters (a `FILTERS` array of value/label pairs) drive chips in the header.

`Row.tsx` is a per-log-type renderer registry: for each `log.parsed_type`, it dispatches to a `summary()` (one-line description), `badge()` (category/label), `rightSide()` (optional metadata), and `Editor()` (inline edit form). Each type gets a mini editor component (`FoodEditor`, `PersonEditor`, `TaskLogEditor`, etc.) that uses `useEditor` to handle mutations.

What just happened to a sidequest is worked out by **diffing the list against the one before it** (`diffTask` in `Tasks.tsx`), not reported by each caller. A due date, a status, a category or a note can be changed by a typed entry, a slash command, a drag between sections or the inline editor, and all of them land through the same `listTasks()` refresh — so one diff catches every path and each mutation site stays ignorant of the animation. The marker it produces (`did-reschedule`, `did-done`, `did-note`, `did-recategorize`) is a class on the row; the animations themselves are CSS, except the post-strike collapse, which has to measure a height. Two consequences worth keeping: the FLIP `capture()` runs inside the diff, *before* `setTasks`, because that is the last moment the old layout is still on screen; and a task marked done is held in the open list in its pre-done form (`leaving`) until the sweep finishes, since going done would otherwise remove the row out from under its own animation.

How an entry announces itself when it first lands is a registry, not a branch: `revealOf(log)` in `Row.tsx` maps a domain — and, for sidequests, the *kind* of change — to one of nine reveals (`decode`, `count`, `stamp`, `settle`, `strike`, `roll`, `wake`, `drift`, `thud`). `decode`, the sweep that wipes your typed sentence away to reveal the parsed row, stays the default, because it's the one that describes parsing itself; anything without a better story keeps it. All nine are CSS, all nine are shorter than the `justParsed` window in `App.tsx` that keeps the markup mounted — shorten that window below the longest animation and rows lose their markup mid-flight.

Solace and soma are the two domains where picking a reveal by domain alone was wrong, and both were on `count` — which animates the figure on the right, a figure neither of them reliably has. A finished sleep's right side is empty and a weight's usually is, so those rows arrived with no animation at all. Solace now splits by state the way sidequests split by action, and into opposite motions: `wake` for a night that is over (the line comes into focus out of a blur while a band of light crosses the row) and `drift` for one that has just started (the line comes down from above and sinks the last of the way, and the zzz swells once). Soma gets `thud`, which is the only reveal that animates `.row` itself and so **replaces** the generic `row-in` entrance rather than stacking with it — one `animation` property, and the later rule wins. It drops the row in and squashes it against the line it lands on, because squash and recover is the whole vocabulary of weight, and the volume figure falls a beat behind so it arrives *with* the landing. `wake`'s light is a stripe in an over-wide gradient walked across by `background-position` on the wrapper, for the same reason `stamp`'s wash lives there: an overlay inside the row paints on top of the words, and the timeline clips anything reaching outside a row. Both of its keyframes carry `background-repeat`, which doesn't interpolate — set once, it would flip halfway.

Two of them need markup the plain row doesn't have, and both are conditional so the row is otherwise untouched: `settle` splits the summary into per-character spans (capped at 64 characters, and only when the summary is a plain string rather than markup), and `strike` wraps the summary in `.row-struck` so the line is as wide as the words — `.row-main` is the flex-grow cell, so drawing across it struck through a foot of empty space. Characters must be rendered verbatim, not with `&nbsp;` for spaces: `useTextFlash` compares `textContent`, and swapping the spaces back at the end of the window read as an edit and flashed the row.

`roll` is the one reveal with a backend half, and it serves two actions. `TaskData` carries `previous_due_date` (set only on a reschedule) and `previous_title` (set only on a rename), so the timeline row can say `monday → friday` or `old name → new name` rather than only where it landed. Both live inside `logs.data`, so no migration — but both are `skip_serializing_if = "Option::is_none"`, and rows written before they existed simply don't have them, which is why `revealOf` falls back to `decode` when one is absent. `models.rs` has tests pinning that shape, since the frontend reads the *absence* of these fields as a decision.

A rename is also the one edit `patch_task` writes a `logs` row for. The others it can apply — a due date, a status, a category, a note — are either already logged when the same change arrives as a typed entry, or are tweaks you make several of in a row and would only clutter the day. Because that write happens outside the timeline, `Tasks.tsx` fires **`life-timeline-stale`** and `Home` listens for it. It deliberately does not listen to the broader `life-log-created`: Home applies its own writes locally, so that would add a redundant round trip per entry to a backend that sleeps between visits. The handler diffs the ids it had before against the ones it has after and hands the new ones to `flashParsed`, which is what gives a row written elsewhere its arrival animation.

The timeline's equivalent is `useTextFlash`, which compares the rendered `textContent` of `.row-main` and `.row-right` across renders and flashes only the one that changed. It compares text rather than props deliberately: the collapsed row shows a summary, not fields, so there is nothing else that reliably corresponds to what the user can see change.

Four things in the sidequests panel move rather than cut, and two of them share a trap. The planner's **overflow warning** is held in local state through its own exit, because pressing "drop x" takes the overflow to nothing in the same response that removes the block — letting the banner vanish on that frame is a hole opening under the list. It enters on `max-height`/`margin`/`padding` keyframes filled `backwards`, never `both`: a forwards fill would leave the ceiling standing at its hand-set 140px and clip a third line of text half a second after the animation ended. Its exit runs through `collapseAndRemove`, which now animates **margins** alongside padding and height, for the reason one step out from the padding rule — an element at zero height still holds its neighbours apart by its margin, so the gap closes all at once at unmount. The **day switch** slides the list under the strip as one block (`.task-list-view`, keyed on the day), directionally: 18px, not the timeline's 42px, since the panel has 24px of padding and nothing clipping it. Its class and key are set in the same handler as the day itself — the entrance has to be committed in the render that first shows the rows it belongs to, which is why both `setSelected` calls funnel through one `pick`. And the **resolved list** uses `Expand` rather than `<details>`, whose open and close are both instant.

A sidequest moved to a day you aren't looking at leaves the list sideways (`flingOut`): it travels right at full opacity, measured to the window edge rather than a fixed distance, and its height, padding, margins and bottom rule collapse from 140ms in so the rows below slide up behind it rather than after it. It is the same held-row mechanism as the done sweep — `leaving` carries a `mode` now, `done` or `away`, and the held copy is the one from *before* the change, which is what gives the exit something to animate and also why its `did-reschedule` marker is suppressed: the old copy would roll its old date up against itself. Three things there are load-bearing. The clip belongs on **`.shell`**, not on the row's section — a transformed row still counts towards the page's scrollable width, so something has to clip or a horizontal scrollbar flashes for the length of the flight, but clipping at the section ate the row at the panel's own edge and it read as sliding under something rather than leaving. The shell is the width of the window, so the row stays visible the whole way out. The mobile panel is `position: fixed` and scrolls itself, so the shell's clip can't reach it and it carries its own `overflow-x: clip`. `openTasks` **sorts by the server's key** (due date, then `created_at`, then id) instead of trusting the order the server sent, because a held row carries its old due date: left alone it sorted by where it had just been moved *to*, jumped to the bottom of the list, and flew off from there. The id is on the end of that sort to make the tie total — two sidequests can share both a date and a creation time, and the row has to land in the same place two renders running. And the flight's curve is deliberately not a steep ease-out: only the panel's own width of travel can be seen, and a launch-shaped curve crossed it in three frames.

Emptying a day is the other half of the same complaint, and both cases are cuts of about seventy pixels. The **overdue heading** is a section of its own, so moving your last late sidequest forward took the heading with it on the frame the row finished leaving; it is held through its own `collapseAndRemove` in the same shape as the planner's overflow warning, keeping the count it had (nobody has ever had "overdue (0)"). The day's **"nothing due" line** grows in rather than appearing at full height, on a `backwards`-filled `max-height` for the reason the overflow warning uses one. Its reduced-motion rule has to be written `.task-section .empty` to match — `.empty` alone is less specific and loses wherever it sits.

The **"waking up the server" notice** is the same held-through-its-own-exit shape a third time (`BackendNotice` in `App.tsx`): the server answering takes it away in the same frame, and everything below it jumped. Its entrance ceiling is `24px` rather than a comfortable one, because a generous `max-height` races past the real height of the one line it is in the first few frames and there is nothing left to see.

Beyond those, the rule the whole app follows now: **anything that unmounts plays an exit first**, and there are only three ways it is done. A fixed-position toast holds itself with `usePanelState` and swaps to a `.closing` class — the focus pill and the sleep nag both do this, and the pill also keeps the last session it was showing in a ref, since there is none left to read by then. Anything a *parent* unmounts plays the exit itself before handing back: `RateModal` sets a `closing` flag and calls `onClose` 180ms later, which is what lets four call sites stay as they are. And anything that is a block of content in flow uses `Expand` (cadences' manage panel and schedule editor, the wishlist's done list, a trip's itinerary — the last of which had `.expand`/`.expand-inner` markup by hand with nothing setting the height). Two traps met along the way: a keyframe that sets `transform` wipes out a `transform` the base rule was using for layout, which is how the sleep nag - centred with `translateX(-50%)` - jumped half its width to the left for the length of its entrance; and the empty-state entrance is scoped to `.list .empty` rather than every `.empty`, because the planner measures its body's height to animate it and would have measured an empty state that was still at `max-height: 0`.

And the shell itself: it is centred, so a panel opening or closing moves the whole of Home by about 220px, and it jumped there and back. `App` measures the column's position every render and, on the render that adds or removes the slot, puts it back where it was and glides it — a FLIP, so no layout is animated and nothing can fight the panel's own entrance. Three things there. The measurement is **`offsetLeft`, never a bounding rect**: a rect includes whatever transform is on the element, so a reading taken during a glide is the animation's own doing, and one taken while a `fill: forwards` transform is still applied poisons every delta after it — the column ended up hundreds of pixels off centre. **Closing does not wait for the layout**: the slot stays mounted until the panel has finished fading, so a FLIP on the unmount left the column sitting still for the length of that fade and only then moving, which is exactly the lag the animation was supposed to remove. The close glides the column preemptively, in the frame the close begins, using the stored no-panel position, and the unmount lands underneath it — the transform is dropped there rather than animated. Re-opening mid-close has to cancel that transform, since the layout it was heading for never happened. And a resize listener refreshes the stored readings, since a resize moves the column for reasons that have nothing to do with a panel and a stale one would be replayed as a glide. Below 900px the panel is `position: fixed` and the column doesn't move at all, so the delta is zero and no animation runs.

Clicking the title reassembles the whole screen. `assemble.ts` is the entire mechanism and it is deliberately not React: it puts `.assembling` on `<html>` for the length of the run and every rule in the assemble section of `styles.css` hangs off that, so the three separate trees involved (Home, the sidequests panel, the day plan) take part without knowing they are and without a single re-render. Restarting on a second click is why the class is removed, `offsetWidth` read, and re-added — a finished animation only re-runs when something about it changes, and the browser has to see the off state before it can see the on state again. The delays are absolute positions on one clock rather than each piece waiting on the one before, which is what keeps the order legible when you read the file; every stagger takes its place from an inline `--i` (the sleep wall's pattern) and is capped with `min()`, since a long day would otherwise cascade past the end of the window.

The title's opening act plays on `AssembleStage`, a **second copy** of the word, fixed and centred, and that is not an implementation detail — it is the fix for the thing that made the first version look cheap. A transform scales the raster the text was already drawn at, so `scale(4)` on a 46px title is a 46px title blown up: soft, stepped, obviously low-resolution. The stage is *drawn* at its full size and scales **down** onto the real one, which is the direction that stays sharp. It is wiped in on a diagonal by an oversized mask — three times the box, opaque for its first half — walked from bottom-right to top-left, and then shrinks into the header. The handover is a **single frame**, not a cross-fade: the stage is 190px type scaled down and the real title is 46px type drawn at 46px, and no two rasterisations of that are identical, so any window where both are part-way visible is a window where you watch one turn into the other. `stage-hold` and `title-handoff` are `steps(1, jump-end)` over the same duration, the same trick the day box's border uses. That only works because the two boxes are geometrically similar, which is why `.brand-stage-word` is a **block sized to its content**: as an inline span its rect carried the line box's strut above and below the glyphs, which the h1's does not, so aligning their centres put the landing twenty pixels out and the word visibly moved as it swapped. Similar boxes plus a width-ratio scale land it to within a twentieth of a pixel.

`measureTitle` reads both rects and hands over `--stage-dx/dy/scale`. It runs **four times** per click, and that is the fix for a landing that was sometimes right and sometimes short: the click usually changes the route too, and opening the panel moves Home's whole column two hundred pixels, so the reading taken before React commits is against a layout that is about to stop being true and the title flew to where the title used to be. It re-reads on the next two frames and again at 400ms, all long before the flight begins — and never during it, since the flight's own transform is in the rect and feeding that back in would send each reading further off than the last. Two other things about the title are each a bug that was fixed: the clip that uncovers the word is on the word itself while anything that has to travel past that clip must not be its descendant, because an ancestor's `clip-path` clips its children; and the clip's insets are in **em, deliberately larger than a line box**, because `.brand-sub` is a block inside an inline, which breaks the inline into fragments so the reference box is only the first line — a percentage measured against it cut "folders." in half.

Typing is one recipe used four times (the two day fields, the panel's title, its quip): an animated `--type` percentage drives a `clip-path` that opens left to right, and the step count is the **character** count, so each step is one letter. `--steps` is handed in where the text is known and applied through `animation-timing-function: steps(var(--steps, 24))` as its own declaration rather than inside the shorthand, so a browser that will not take a `var()` there loses the stepping instead of the animation. The percentages are of the element's own width, which is why everything typed is an element sized to its text: `.brand-word` exists for that reason (the title was a bare text node in the h1), and `.panel-quip` carries `width: fit-content` for it. There is no caret — there was one, and it is worth knowing why it failed, because the same trap is waiting for anything drawn at the reveal's edge: it was a pseudo-element, `--type` was registered `inherits: false`, and a pseudo cannot see a value that does not inherit, so it sat at nought per cent for the whole animation while the text revealed itself behind it. `--type` is `inherits: true` now. Each typed element is also **gated** as well as swept, because the clip's own first frame leaves a few pixels of the first letter showing, which for the quip was a stray mark under the title for two seconds before its turn.

The day box's outline is drawn clockwise by an overlay carrying the same 1px border, revealed by a `conic-gradient` mask whose angle animates 0deg→360deg (`@property --draw`). Three things about it, each a twitch that had to be chased: the overlay is `inset: -1px`, because an absolutely positioned child measures from the *padding* box, so at `0` its border sat a pixel inside the real one and the outline jumped outward when they swapped; it must hand the border back and **go**, since left up it stood a second line on top of the real one for the rest of the run; and the handover is two `steps(1, jump-end)` animations of the same duration and delay, so the real border comes on in the very frame the drawn one leaves. Easing them across each other leaves a window with two lines painted or none, and either reads as a flicker.

The day strip is the one piece that is not a CSS animation. It only reaches five days into the past — a hundred and fifty pixels, nothing to scroll — so `DueStrip` lays down `RUNWAY_DAYS` real columns to the left for the run, throws the scroll along them and takes them away again; today is at the strip's left edge before and after, so removing them moves nothing. It is a real scroll rather than a transform because a transform is a picture of scrolling and cannot land on a column, the easing is a plain cubic ease-out (thrown, then friction — nothing about it is at a constant rate), and it starts 250ms before the strip fades in so it is already moving when you first see it. The target is measured off the **rects**, not `offsetLeft`, and that is the trap: the strip is not positioned, so a column's `offsetParent` is the *panel*, and `offsetLeft` came back 24px large — the panel's own padding — so the strip landed a sliver past the day it was aiming at. `STRIP_START_MS`/`STRIP_RUN_MS` live in `assemble.ts` and must stay in step with the strip's delays in the stylesheet; a panel that mounts *because* of the click misses the `life-assemble` event, so it asks `assembleElapsed()` instead of listening.

Three rules govern everything here, and all three are things that have gone wrong. **Nothing may sit on an element that already carries an `animation` of its own** — `.row`, `.side-panel`, `.task-list-view` — because replacing one means the name in that slot changes *back* when the class comes off, which starts it again seconds later; that is exactly the bug the soma reveal shipped with. **Nothing may change layout**: `display: inline-block` on the title's link, to give the clip a box, changed the height of the header's line box, so the nav sat 23px low for the whole run and snapped back up at the end taking every row below it along. Only `position: relative`, `z-index`, transforms and animations are allowed, and the `position: relative` declarations that can safely be permanent are permanent, in the base rules, so that the page is not one thing during a run and another after it. And **the screen has to be empty until each piece is called**, which does not follow from each piece being animated: an animation filled `both` holds its 0% frame through its own delay, so a 0% frame that is only half-hidden — a clip band, a flash line, a caret at full opacity — parks that fragment on screen for seconds. Every container is gated by `hud-gate` at the moment its contents begin, and every keyframe set that can show something starts at `opacity: 0`.

The shell's own FLIP glide is suppressed for the duration (`isAssembling()` in `App`): the assemble re-forms the column where it finally stands, so sliding the column itself from where it used to be fights it. A `--flash` token carries the bright line the entry box is built from — white on the dark theme, where it reads as light on an edge, and the accent on the cream, where nothing is brighter than the page; that line draws itself across the middle of the box, swoops down and becomes the underline, and the input's own border has to be painted *before* the line starts fading or the handover reads as a blink. The day strip's spin is pure appearance: `DueStrip` already scrolls today to `inline: 'start'` on mount, so the animation only has to look like the journey — a very long throw, blurred, decelerating hard — and never touches `scrollLeft`, which by then may be where the user put it.

New reduced-motion rules for anything defined *below* the shared `animation: none` block at the bottom of the domain styles need their own `@media` block — the shared one loses on source order at equal specificity.

`checkHealth` in `api.ts` carries a 3s timeout, and that timeout is the entire point of the function. A sleeping Render service does not refuse the connection — it holds it open for the 30-60s the container takes to boot and then answers 200 — so without a deadline it never returns false and the "waking up the server" notice never appeared for the one situation it exists for. `Home.submit` needs the same reasoning: a cold backend doesn't reject, so the catch never fires, and the notice is armed by a 2.5s timer instead.

One trap that cost four separate visual bugs: `overflow-x: clip` was set on `.list`, but `.list` is the timeline *and* every panel's main column. The day slide needs the clip; the sidequest panel needs the opposite, since a drag-over outline sits 4px outside its section and a row's accent edge sits 8px outside the row. It is `.day-list` now — check what else wears a class before styling it for one caller. The timeline still clips, which is why nothing there may reach outside a row either: the `stamp` reveal's accent flash is a `background` animation on `.row-wrap` via `:has()` rather than a bar at `left: -10px`, because the bar was cut off and an absolutely positioned overlay inside the row paints on top of the text.

Motion on the timeline lives in `frontend/src/motion.ts` plus keyframes in `styles.css`, all of it dependency-free. Three things there are worth not relearning. `useFlipList` does **not** remember positions across renders — the caller calls `capture()` immediately before whatever is about to reorder the list (the filter chips, and the sidequest diff described above). Storing a map across renders was tried and is wrong: expanding a row changes layout through a CSS transition, which re-runs no effect, so the map went stale and closing the row yanked every row below back to its pre-expand position and glided it down again. Capturing on demand also means expanding, deleting and changing day never trigger a FLIP, and the layout effect reads no layout at all when nothing was captured — which matters because typing in the entry box re-renders Home. `collapseAndRemove` animates a measured pixel height (not `auto`, which isn't animatable) before the row leaves the DOM, so the rows below slide up — and it must animate the **padding** down alongside it, because `box-sizing: border-box` is global, so the used height floors at padding-top + padding-bottom and the element stalls there before vanishing, which is a snap of exactly that many pixels at the very end. The timeline's grey notice ("moved x, cmd+Z to undo") is dismissed through the same helper rather than a bare `setNotice(null)`; a generation counter guards the removal, since a notice replaced mid-fade would otherwise be cleared by the outgoing run's `oncancel`, which fires a beat after `cancel()` returns. And the decode sweep in `Row.tsx` is an overlay of `log.raw_input` clipped from its left edge, which means the `justParsed` window in `App.tsx` must outlast the sweep's duration in CSS — they are coupled, and 500ms against a 520ms animation cut it off a frame early.

The day-change slide took three attempts and the failures were all the same shape: **an entrance animation has to be committed in the same render as the content it is animating.** Keying it to `date` ran it on the day you were leaving, because the fetch hadn't resolved yet. Holding the direction in its own state fixed that but restarted the animation in place the moment you reversed direction — the class changed on an already-mounted list with no remount to go with it. Both the `slide-*` class and the `key` now come from one `view` object that `refresh` sets alongside the rows.

The mic level is the one place a value is written straight to the DOM rather than through state: the analyser writes `--l0`..`--l4` onto the button at 60fps, because re-rendering Home (and the whole timeline beneath it) that often would be absurd.

Voice input is wired end-to-end: hold the mic button in the input area → `MediaRecorder` → `POST /api/transcribe` (Whisper) → `groq::polish()` (small model cleanup) → text appended to the input box → submit flows through the normal parse pipeline. New entity types get voice capture for free once a tool def exists.

## Constraints

- **Auth**: single shared bearer token (not per-user — all edits share one `AUTH_TOKEN` env var). There is no multi-user account model, no session management, no OAuth.
- **Deployment**: Render free web service (sleeps after 15 min idle, no background worker / cron process). If proactive features (daily email, scheduled reminders) are needed later, they must be triggered externally (e.g. GitHub Actions cron job) hitting an HTTP endpoint.
- **Frontend deployment**: NOT auto-deployed on push. Run `scripts/deploy-frontend.sh` locally to build and push the static output to the sibling `dotfolders` repo, which GitHub Pages then serves.

## Conventions

- **Minimal comments**: default to none. Add only when the WHY is non-obvious (hidden constraint, subtle invariant, bug workaround, behavior that surprises readers).
- **No premature abstraction**: three similar lines is better than a generic helper; don't design for hypothetical future requirements.
- **No error-handling for impossible scenarios**: trust internal code and framework guarantees; validate only at system boundaries (user input, external APIs).
- **Reuse existing patterns**: JSONB-in-logs for lightweight entities, `Action` enum dispatch for side effects, `*_context_block` for state injection, `Row.tsx` per-type cases for timeline rendering, hash routes for dashboard pages.
